# Per-module coverage on pull requests

Report, on every pull request, how well tested the modules that ran actually are — and whether the
files this pull request changed were tested at all.

## Context

This repository already asks for code coverage. `Module+Schemes.swift` sets `coverage: true` on
every module scheme, with `codeCoverageTargets` narrowed to the module itself, and the `Less Paper`
scheme sets it across `Module.allCodeCoverageTargets` — the 28 modules that `Module.swift` marks as
`codeCoverageTarget`. None of it reaches CI. `test-unit.xcresult` from the last run on `main`
answers `xcrun xccov view --report` with "No coverage data in result bundle".

The reason is that **CI never runs any of those schemes.** `mise/scripts/run_tests.sh` invokes
`tuist test` with no scheme argument, so xcodebuild runs the workspace scheme Tuist synthesises, and
that scheme is not one of ours. `LessPaper-Workspace.xcscheme` carries no `codeCoverageEnabled`
attribute at all — which means off — and zero `CodeCoverageTargets` elements, while the generated
`Logging.xcscheme` beside it has `codeCoverageEnabled = "YES"` and its framework listed. The
coverage configuration is real; it is attached to schemes that only ever run locally.

Merging was ruled out as a suspect along the way, since `tuist test` produces one bundle from a run
that covers many schemes: `xcrun xcresulttool merge` preserves coverage data, so nothing is being
lost after collection. The data was never collected.

Running the `Logging` scheme alone confirms the rest of the pipeline works. The bundle reports
`Logging.framework 70.81% (228/322)` across 8 files, `xcrun xccov view --report --json` gives
per-file `coveredLines` and `executableLines` against absolute paths, and `xcrun xcresulttool get
test-results tests` names the executed bundle as `LoggingTests`. Everything this design needs is
already in the result bundle the CI job produces — once the run is asked to collect it.

### What the report is for

The audience is a reviewer, not whoever is debugging the run. That distinction drives two of the
decisions below, and it is worth stating plainly: this is the first thing in this repository whose
output is aimed at the pull request conversation rather than at the run that produced it.

## Decisions

**Only what ran is reported.** Tuist selective testing means a pull request tests the modules whose
fingerprint changed and nothing else. The report covers exactly that set. No baseline is stored, no
snapshot of `main` is carried forward, and no module is shown with a number that some earlier run
measured. A coverage table that mixes fresh and remembered numbers has to explain which is which
every time it is read, and the explanation is never as short as the table.

**A module is listed only when its own test target ran.** If `DocumentsFeatureTests` runs,
`DocumentsFeature` is listed. `Components` is not listed on the strength of being a dependency that
`DocumentsFeature` happens to exercise. Coverage measured sideways through somebody else's test
suite is not information a reviewer can act on, and printing it invites reading a shared module's
number as if its own tests had earned it.

**The numbers themselves stay suite-wide.** This is the honest limitation of the decision above. The
whole suite runs as one scheme, so coverage is aggregated across the run: when `ComponentsTests` and
`DocumentsFeatureTests` both run, `Components` is listed, and its percentage counts lines reached by
`DocumentsFeatureTests` too. Isolating each module's number would mean one `tuist test <scheme>`
invocation per selected module rather than one run in total, and the bill comes due precisely on the
wide-blast-radius pull requests — a change to `ApiInterface` reselects everything, and the single
self-hosted runner would pay roughly 27 generate-and-build cycles for it. The filter above already
removes the misleading rows in the common case, where the shared module was not itself touched and
so was never selected. `AppSnapshots` is the clearest remaining inflator: it drives the real app, it
is not named `…Tests` so it is never listed itself, and every feature module it walks through gains
coverage from it.

**The report never fails the build.** Whether the job is green stays entirely a question of whether
the tests passed. There are no thresholds, so there is no per-module baseline table to maintain and
no false red on a pull request that legitimately adds uncovered code. The generator is nonetheless
split into extraction and rendering, with machine-readable numbers in between, so that adding a gate
later is a change rather than a rewrite.

## Collecting coverage

One change, in `Workspace.swift`:

```swift
generationOptions: .options(
    autogeneratedWorkspaceSchemes: .enabled(
        codeCoverageMode: .targets(Module.allCodeCoverageTargets)
    ),
    lastXcodeUpgradeCheck: Version(26, 5, 0)
)
```

`CodeCoverageMode` defaults to `.disabled`, which is the whole of the bug described above. Passing
`Module.allCodeCoverageTargets` rather than `.all` or `.relevant` keeps the instrumented set defined
in exactly one place, `Module.swift`'s `codeCoverageTarget`, which is where it is already decided
for the per-module schemes.

`.enabled`'s remaining defaults — `testingOptions: []`, and `nil` for `testLanguage`, `testRegion`
and `testScreenCaptureFormat` — match what the synthesised scheme already has, so naming the
parameter changes nothing else. The language and region the suite runs under come from the
`-testLanguage en -testRegion DE` that `run_tests.sh` passes on the xcodebuild command line, and are
unaffected either way.

The per-module schemes keep their own `coverage: true` and stay the right thing to run locally, where
a single scheme does give a module's number in isolation.

## Deciding which modules are listed

`mise/scripts/coverage_report.py` reads two things out of the bundle:

- `xcrun xccov view --report --json` — every instrumented target with `coveredLines`,
  `executableLines` and `lineCoverage`, and the same per file with an absolute path.
- `xcrun xcresulttool get test-results tests --format json` — the test hierarchy, whose
  `Unit test bundle` nodes name the test targets that actually executed.

The filter is the intersection. Each executed bundle named `FooTests` maps to `Foo`, and survives
only if `Foo.framework` appears in the coverage report. That second half is not a formality: it is
what keeps the module list out of the script. Because the workspace scheme now instruments exactly
`allCodeCoverageTargets`, the coverage report *is* the list of coverage targets, and the script never
needs its own copy of a set that `Module.swift` already owns.

Targets that do not end in `Tests` map to nothing and are never listed. That is the correct outcome
for `AppSnapshots` and `AppUITests`, which cover other modules rather than one of their own.

Of the 28 coverage targets, 27 have a matching test target. `DesignTokens` is the exception — there
is no `DesignTokensTests` — so it can never appear in the table. This matters in the next section.

## The report

Two sections, in a single comment.

**Modules.** One row per listed module: name, percentage, and `covered/executable` lines. Under
selective testing this is usually a handful of rows; on a pull request that reselects everything it
is at most 27.

**Files changed in this pull request.** The added and modified files under `Modules/**/*.swift`,
excluding test sources, joined to the per-file coverage by absolute path. This is the section that
answers the question a reviewer actually has, which is not "where does this project stand" but "did
this pull request test what it added". A new file landing at 0% is invisible inside a module-level
percentage and unmissable here.

The diff is taken against `github.event.pull_request.base.sha`, passed in to the script, rather than
against `origin/main`. `actions/checkout` fetches to depth 1, so `origin/main` is not a ref the
runner can be relied on to have — it happens to survive on this self-hosted runner because `ci.yml`
checks out with `clean: false`, which is an accident of the runner rather than something to build
on. Deletions are filtered out with the test sources: a removed file has no coverage to report and
is not a gap in what the pull request tested.

A changed file whose module has no coverage row is reported as not measured, never as 0%. The live
case is `DesignTokens`, which is instrumented but has no test target, so its files are never covered
by a run no matter how healthy the suite is. Rendering that as 0% would read as a regression caused
by the pull request, which is the one thing this report must not do. The same rendering covers the
rarer case of a module whose tests were not selected.

## Posting

A new `mise/tasks/ci/coverage`, run as a step in the `test_unit` job after `ci:test:unit`, guarded to
`pull_request` events — a push to `main` has no pull request to comment on.

**This breaks a convention deliberately.** Every workflow in this repository reports through
`GITHUB_STEP_SUMMARY` and nothing has ever posted a pull request comment, though `ci.yml` has held
`pull-requests: write` all along. A step summary on a green check is something nobody opens, and the
entire value of this feature is that coverage reaches a reviewer who was not looking for it. The
comment is posted instead of a summary, not in addition to one; two copies of the same table would
only raise the question of which is current.

The comment is sticky. An HTML marker — `<!-- coverage-report -->` — identifies it among the pull
request's comments via `gh api repos/{owner}/{repo}/issues/{number}/comments`, and the run either
PATCHes that comment or POSTs a new one. A pull request accumulates pushes, and a column of
superseded coverage tables is worse than no table.

When the bundle is missing, the comment is rewritten to say that no modules were tested rather than
left alone. `run_tests.sh` already treats a missing bundle as a legitimate outcome — selective
testing finding nothing to do is a pass — and a table left standing from two pushes ago would be
read as describing the current head.

## The JSON in between

The script extracts to a plain structure — per-module and per-file names, covered lines, executable
lines — and renders markdown from that structure alone. Nothing about the layout of a result bundle
survives into the rendering half.

This is the whole of what "shaped so a gate can be added later" means. A future per-module threshold
reads the extracted numbers; it does not re-parse an xcresult, and it does not scrape a table out of
markdown.

## Testing

Rendering is a pure function of the extracted structure, so it is tested directly, against a fixture
captured from a real bundle. The `xcrun` calls sit behind a thin extraction layer that the tests do
not exercise.

There is no Python test convention here yet — neither `fastlane/metadata_lint.py` nor
`mise/scripts/attribute_blank_lines.py` has tests — so this establishes one, using `unittest` from
the standard library rather than adding a tool. `mise ci:lint` grows a
`python3 -m unittest discover` alongside the checks it already runs.

The cases worth covering are the ones where the report could mislead rather than merely look wrong:
a module whose tests did not run is absent; a changed file in a module with no test target reads as
not measured rather than 0%; a run with no bundle produces the "nothing was tested" comment.

## Out of scope

**Baselines and deltas.** No snapshot of `main`'s coverage, no "+2.1%" against it, no whole-project
number on a pull request that tested four modules. Considered and declined: it buys a project-wide
picture at the price of storing and refreshing state outside the run, and every number in the table
then needs a provenance.

**Per-module isolation.** Declined for the cost described under Decisions. If the suite-wide numbers
prove misleading in practice, the way back is per-scheme runs, and the filter and rendering here are
unaffected by that change.

**Gating.** No thresholds, no required minimum, no failing the job on a drop.

**Per-file drill-down beyond changed files.** `xcresultparser --coverage-report-format classes`
renders every file in every tested module, folded or not, and it is noise on the overwhelming
majority of pull requests.

**A step summary.** See Posting.
